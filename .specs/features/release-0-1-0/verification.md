Own examples run at 615f6c4 as a throwaway spec (deleted, all green): a tag on an older commit of `main` passes; a missing `origin/main` ref fails closed with the "not on main" message; `v0.2.0-rc.1` against `0.2.0-rc.1` passes, while `0.2.0-rc.1` and `v0.2.0` fail; `verify-install.mjs` passes through a 302 redirect to the tested tarball, and fails for a different valid tarball with the same name and version, and for an HTML page; `notes.mjs` builds a correct prerelease URL.

Confirmed against the docs or source: the default `run` shell is `bash -e {0}`; a job `if` without a status function gets an implicit `success()`; a failed or skipped `needs` skips the whole chain; `GITHUB_REF_NAME` is the tag name; `actions/checkout` with `fetch-depth: 0` fetches `+refs/heads/*:refs/remotes/origin/*`, so `origin/main` exists. In gh, `--draft` sets `draftWhileUploading` to false, so a failed upload leaves the draft in place and gh does not delete it. gh checks that the asset files exist before it creates the release, and `--verify-tag` aborts before creation. With `--generate-notes`, gh sends the body together with `generate_release_notes: true`, and the REST docs say the body "will be pre-pended to the automatically generated notes". Upload `.pack/*.tgz` puts the file at the artifact root, and download `name: tarball` with `path: .pack` brings back `.pack/gabrioliv-dossier-<v>.tgz`. `upload-artifact@v7` and `download-artifact@v8` exist, and v8 fails on a digest mismatch by default.

Not confirmed (needs a real GitHub run): whether the public asset URL answers right after `gh release edit --draft=false`, and whether a repository setting for immutable releases interferes. Uploading while the release is a draft is the compatible path for that setting.
